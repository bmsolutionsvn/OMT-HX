# OMT-HX H.264 Codec Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an OMT-HX source send H.264 instead of HEVC, chosen per source by the sender, with one receiver that reads either without a setting, the way NDI HX3 offers both codecs.

**Architecture:** H.264 access units travel exactly as HEVC ones do today: as ordinary OMT video frames, under a second codec tag, `H264`. The libomt patch learns that tag. Inside `omthx`, a new public `Codec` value is threaded through the pure functions, `Encoder`, `Decoder`, `Sender` and `Receiver`; the receiver picks its decoder from the tag on each frame.

**Tech Stack:** C++20, MSVC (Visual Studio 2026), CMake + Ninja, vcpkg (FFmpeg, doctest), .NET 8 SDK (only to build libomt), Windows PowerShell 5.1 scripts. Windows x64 only. No new dependency.

**Spec:** `docs/superpowers/specs/2026-10-12-omt-hx-design.md`, plus the Decisions section below, which Task 5 copies into the spec as section 17.

## Decisions

These are new. D5 and D6 are starting values the owner should confirm.

| # | Topic | Decision |
|---|---|---|
| D1 | Who chooses | The sender, per source: `Codec::Hevc` (the default) or `Codec::H264`. The receiver has no setting; it reads the tag on each frame. |
| D2 | Carriage | A second codec tag, `H264`, the 32-bit value `0x34363248`. The spec's section 4 already says a later format gets its own tag. |
| D3 | H.264 on the wire | 8-bit 4:2:0, full-range BT.709, progressive, no B-frames, Annex B. Every keyframe is an IDR picture (NAL type 5) with SPS and PPS in the same access unit. The profile is the encoder's choice (Main or High). |
| D4 | Encoder | The first of `h264_nvenc`, `h264_amf`, `h264_qsv`, `h264_mf` that opens. No software encoder. |
| D5 | No fallback between codecs | If the chosen codec has no hardware encoder, `Sender` throws and names what it tried. It never switches codec by itself, because the operator chose the codec for a reason. |
| D6 | Bitrate | H.264 uses 1.4 times the HEVC bitrate of the same quality level. At 1080p60 that is 21, 42 and 70 Mbps. Unmeasured; tuned in Task 5. |
| D7 | Codec change on a live source | When a source comes back with the other codec, the receiver rebuilds its decoder and waits for a keyframe. No restart. |

## Status (2026-10-13)

Proven on this PC today, by throwaway runs and not by this repository's tests:

- `h264_amf` opens with `-usage ultralowlatency -rc cbr -forced_idr 1 -bf 0` at 1920x1080 and at 1920x2176 (the packed-alpha size), 60 fps. Output: Main profile, full range, no B-frames. A 30 Mbps target gave about 34 Mbps, the same as `hevc_amf` on the same input.
- A forced keyframe from `h264_amf` is one access unit holding AUD (9), SPS (7), PPS (8), IDR (5), in that order.

- The 1920x2176 stream is labelled level 5.0, which is below what that size needs at 60 fps. Whether D3D11 decodes it is checked in Task 5.
- `omthx-recv` kept running while `omthx-send` was stopped and started again under the same name: pictures returned by themselves about 3 seconds later.
- `h264_amf`, `hevc_amf`, `h264_mf` and `hevc_mf` all refuse a 16384x16384 picture with an error, not a hang. Task 3 uses that size to test the "no encoder opens" path.
- `git diff` inside `build\omt-src\libomtnet` reproduces `patches\libomtnet-hx.patch` byte for byte, so Task 1 can regenerate the patch that way.

## Review Focus

Inputs this change implies that are easy to miss. Each has a test in the task named, except the last.

1. **The operator switches a running camera from HEVC to H.264.** BreadCamera will destroy the `Sender` and create one with the same name. A receiver that stays connected must show the new stream, not error forever on a stale decoder. Task 4 (codec-switch test).
2. **Bytes of one codec meet the other codec's decoder or keyframe test.** That must be an error or "not a keyframe", never a crash or a picture. Task 2 (cross-codec keyframe test), Task 3 (cross-codec decoder test).
3. **An H.264 keyframe that does not start with its IDR.** AMD puts AUD, SPS and PPS first, so the keyframe test must look at every NAL unit, and only an IDR may count. Task 2 (H.264 NAL test).
4. **The chosen codec has no encoder for this picture.** For example H.264 at a size beyond its limit. `Sender` must throw `std::runtime_error` naming all four encoders of that codec and must not fall back to the other codec. Task 3 (oversized-picture test).
5. **`Mode::Full` with a codec argument.** The codec must be ignored and VMX sent. Task 4 (plain OMT test passes `Codec::H264`).

No test here, because this PC cannot produce it: **an H.264 source meets a receiver built before this change, or a stock OMT program.** It gets audio and no picture, as a stock program does with HEVC today. Task 5 writes that into the README.

// Proves the patch: HEVC- and H264-tagged frames pass through libomt untouched, and plain OMT is unchanged.
#include <doctest/doctest.h>

#include <chrono>
#include <cstring>
#include <vector>

#include <libomt.h>

namespace {
constexpr int kHevc = 0x43564548;
constexpr int kH264 = 0x34363248;
constexpr char kAsk[] = "<OMTHX Keyframe=\"true\" />";
}  // namespace

TEST_CASE("libomt: HEVC and H264 frames pass through and plain OMT still works") {
  omt_send_t* tx = omt_send_create("omthx-test-libomt", OMTQuality_Default);
  REQUIRE(tx != nullptr);
  char address[OMT_MAX_STRING_LENGTH] = {};
  omt_send_getaddress(tx, address, sizeof(address));
  omt_receive_t* rx =
      omt_receive_create(address, static_cast<OMTFrameType>(OMTFrameType_Video | OMTFrameType_Metadata),
                         OMTPreferredVideoFormat_UYVYorBGRA, OMTReceiveFlags_None);
  REQUIRE(rx != nullptr);

  std::vector<uint8_t> payload(1000);
  for (size_t i = 0; i < payload.size(); ++i) payload[i] = static_cast<uint8_t>(i * 7);
  std::vector<uint8_t> uyvy(1280 * 720 * 2, 128);
  const int alphaFlags = OMTVideoFlags_Alpha | OMTVideoFlags_PreMultiplied;

  bool hevc = false, h264 = false, plain = false, asked = false, tally = false;
  int64_t timestamp = 1;
  const auto deadline = std::chrono::steady_clock::now() + std::chrono::seconds(10);
  while (std::chrono::steady_clock::now() < deadline && !(hevc && h264 && plain && asked && tally)) {
    OMTMediaFrame f = {};
    f.Type = OMTFrameType_Video;
    f.Timestamp = timestamp;
    timestamp += 166667;
    f.Width = 1280;
    f.Height = 720;
    f.FrameRateN = 60;
    f.FrameRateD = 1;
    f.AspectRatio = 16.0f / 9.0f;
    f.ColorSpace = OMTColorSpace_BT709;
    if (!hevc || !h264) {  // first HEVC until it arrives, then H264 until it arrives
      f.Codec = static_cast<OMTCodec>(hevc ? kH264 : kHevc);
      f.Flags = static_cast<OMTVideoFlags>(alphaFlags);
      f.Data = payload.data();
      f.DataLength = static_cast<int>(payload.size());
    } else {
      f.Codec = OMTCodec_UYVY;
      f.Stride = 1280 * 2;
      f.Data = uyvy.data();
      f.DataLength = static_cast<int>(uyvy.size());
    }
    omt_send(tx, &f);

    if (OMTMediaFrame* r = omt_receive(rx, OMTFrameType_Video, 20)) {
      const int codec = static_cast<int>(r->Codec);
      if (codec == kHevc || codec == kH264) {
        const bool intact = r->Data == nullptr && r->CompressedLength == static_cast<int>(payload.size()) &&
                            std::memcmp(r->CompressedData, payload.data(), payload.size()) == 0 && r->Width == 1280 &&
                            r->Height == 720 && static_cast<int>(r->Flags) == alphaFlags;
        if (codec == kHevc) hevc = intact;
        else h264 = intact;
        OMTTally program = {0, 1};
        omt_receive_settally(rx, &program);
        OMTMediaFrame m = {};
        m.Type = OMTFrameType_Metadata;
        m.Data = const_cast<char*>(kAsk);
        m.DataLength = sizeof(kAsk);
        omt_receive_send(rx, &m);
      } else if (r->Codec == OMTCodec_UYVY) {
        plain = r->DataLength == 1280 * 720 * 2;
      }
    }
    while (OMTMediaFrame* m = omt_send_receive(tx, 0)) {
      if (m->Data && std::strstr(static_cast<const char*>(m->Data), "<OMTHX Keyframe")) asked = true;
    }
    OMTTally t = {};
    omt_send_gettally(tx, 0, &t);
    if (t.program == 1) tally = true;
  }
  omt_receive_destroy(rx);
  omt_send_destroy(tx);

  CHECK(hevc);   // the patch, first tag
  CHECK(h264);   // the patch, second tag
  CHECK(plain);  // VMX in, UYVY out, as before
  CHECK(asked);  // a receiver's message reaches the sender
  CHECK(tally);
}
```

int64_t targetBitrate(const VideoFormat& f, Quality q, Codec codec) {
  static constexpr double kBitsPerPixel[] = {0.12, 0.24, 0.40};
  double bits = kBitsPerPixel[static_cast<int>(q)] * f.width * f.height * f.fpsN / f.fpsD;
  if (f.alpha) bits *= 1.25;
  if (codec == Codec::H264) bits *= 1.4;  // H.264 needs more bits than HEVC for the same picture

namespace {
// Calls fn(type) for each NAL unit and stops at the first true.
// The type sits in a different place in each codec's NAL header byte.
template <typename F>
bool anyNal(Codec codec, std::span<const uint8_t> d, F fn) {
  for (size_t i = 0; i + 3 < d.size(); ++i) {
    if (d[i] == 0 && d[i + 1] == 0 && d[i + 2] == 1) {
      const int header = d[i + 3];
      if (fn(codec == Codec::H264 ? (header & 0x1F) : ((header >> 1) & 0x3F))) return true;
      i += 2;
    }
  }
  return false;
}
}  // namespace

  return anyNal(codec, d, [type](int t) { return t == type; });
}

bool isKeyframe(Codec codec, std::span<const uint8_t> d) {
  return anyNal(codec, d, [codec](int t) { return codec == Codec::H264 ? t == 5 : (t >= 16 && t <= 23); });

std::vector<Packet> Encoder::encode(const Nv12& pic, bool forceKeyframe) {
  if (pic.width != ctx_->width || pic.height != ctx_->height)
    throw std::invalid_argument("the picture has the wrong size for this encoder");
  // The frame borrows the picture's memory; FFmpeg copies it inside avcodec_send_frame.
  av_frame_unref(frame_);
  frame_->format = AV_PIX_FMT_NV12;
  frame_->width = pic.width;
  frame_->height = pic.height;
  frame_->data[0] = const_cast<uint8_t*>(pic.y.data());
  frame_->linesize[0] = pic.width;
  frame_->data[1] = const_cast<uint8_t*>(pic.uv.data());
  frame_->linesize[1] = pic.width;
  frame_->color_range = AVCOL_RANGE_JPEG;
  frame_->colorspace = AVCOL_SPC_BT709;
  frame_->pts = index_++;
  frame_->pict_type = forceKeyframe ? AV_PICTURE_TYPE_I : AV_PICTURE_TYPE_NONE;

  const int rc = avcodec_send_frame(ctx_, frame_);
  if (rc < 0) throw std::runtime_error(std::string(codecName(codec_)) + " encode failed: " + averr(rc));
  const int firstParameterSet = codec_ == Codec::H264 ? 7 : 32;  // SPS; VPS
  std::vector<Packet> out;
  while (avcodec_receive_packet(ctx_, packet_) >= 0) {
    Packet p;
    p.data.assign(packet_->data, packet_->data + packet_->size);
    p.keyframe = isKeyframe(codec_, p.data);
    // Safety net for an encoder that keeps its parameter sets out of band.
    if (p.keyframe && !hasNalType(codec_, p.data, firstParameterSet) && ctx_->extradata_size > 4 &&

      p.data.insert(p.data.begin(), ctx_->extradata, ctx_->extradata + ctx_->extradata_size);
    }
    out.push_back(std::move(p));
    av_packet_unref(packet_);
  }
  return out;

## 17. H.264 as a second HX codec

Added 2026-10-13. An HX source sends HEVC or H.264, chosen per source by the
sender, the way NDI HX3 offers both. HEVC stays the default and is unchanged.

| # | Topic | Decision |
|---|---|---|
| D1 | Who chooses | The sender, per source: `Codec::Hevc` (the default) or `Codec::H264`. The receiver has no setting; it reads the tag on each frame. |
| D2 | Carriage | A second codec tag, `H264`, the 32-bit value `0x34363248`. The libomt patch passes it through exactly as it passes `HEVC`; the patch is now 32 added lines. |
| D3 | H.264 on the wire | 8-bit 4:2:0, full-range BT.709, progressive, no B-frames, Annex B. Every keyframe is an IDR picture with SPS and PPS in the same access unit. The profile is the encoder's choice. |
| D4 | Encoder | The first of `h264_nvenc`, `h264_amf`, `h264_qsv`, `h264_mf` that opens, with the same per-vendor low-delay settings as HEVC. No software encoder. |
| D5 | No fallback between codecs | If the chosen codec has no hardware encoder, the sender fails with an error naming what it tried. |
| D6 | Bitrate | 1.4 times the HEVC bitrate of the same quality level: 21, 42 and 70 Mbps at 1080p60. A starting value; picture quality has not been compared by eye. |
| D7 | Codec change on a live source | When a source comes back with the other codec, the receiver rebuilds its decoder and waits for a keyframe. |

Why: H.264 has a hardware encoder on every GPU, including ones too old for
HEVC, and it is the simpler codec. Measured figures for both are in
`docs/MEASUREMENTS.md`.

What H.264 does not change:

- It is covered by a patent pool, as HEVC is (section 14). It is not the
  royalty-free option; AV1 still is.
- Alpha packing, keyframe rules, discovery, audio and tally are the same for
  both codecs.
- A receiver built before this section, like a stock OMT program, sees an
  H.264 source with audio and no picture.

One difference in behaviour: left alone, AMD's H.264 encoder sends very few
IDR pictures, so H.264 depends on the sender forcing a keyframe every
2 seconds (section 8). It already does.
```
